A pointer, four levels deep

A pointer is one 8-byte number, and that number is an address — the location of some other data, not the data itself. Two names for one storage: write through the address and the original changes, because there was only ever one box. Pick an action and watch.

Level 1 was what it is. Now the case where not using a pointer is the wrong call: you want a procedure to change the caller's data — and without a pointer it physically cannot.

A Player passed by value is copied into the procedure. The procedure can scribble on its copy all it likes; when it returns, the copy is gone and the caller's Player never moved. Pass a ^Player instead and the procedure shares the caller's exact storage (Level 1's aliasing) — now the write sticks. Press the button to run both against the same starting hp = 20:

The counterfactual: if your procedure only reads a small value — an int, a tiny struct it never changes — a pointer buys you nothing; pass the value and let it copy. The pointer earns its keep precisely when you need shared mutation (the callee changes what the caller holds) or want to skip copying something large every call. No mutation, no bulk — no pointer.

Return the whole struct and reassign (p = heal(p, 30)): works, but it copies the struct out and back every call — fine for an int, wasteful for anything fat, and it can't touch a value the caller didn't hand back (e.g. one element of an array in place).

A package-level global: now any two call sites fight over one piece of state, and the dependency is invisible at the call — the classic source of "why did this change?" bugs.

Pass by value and mutate: doesn't work at all — that's the left column above, hp stays 20. (In C#, by contrast, you'd reach for a ref parameter here; Odin has no ref keyword — you write the ^Player out loud, which is the same thing, just visible.)

Level 2 sold you on the pointer. Level 3 is the bill: a pointer is just an address — it has no idea whether the thing at that address is still alive. Keeping the target alive is your job, and the language will not stop you from getting it wrong.

Here is the footgun. A procedure makes a local, hands back its address, and returns — the local's storage is reclaimed the instant the procedure exits, but the address you returned still names that now-reused spot. Step through it:

inside dangling()
local = 7
returned address ──▶ local

The good news: Odin has a targeted escape check that rejects the direct shape at compile time. Returning &local straight out of a procedure does not build:

dangling :: proc() -> ^int {
    local := 7
    return &local   // the obvious dangle
}

Error: It is unsafe to return the address of a local variable ('&local') from a procedure

The bill, in full: that check guards the obvious shape, not lifetimes in general. An address that escapes indirectly — stored through an out-pointer, parked in a struct that outlives the call, or held past an arena reset — compiles in silence and dangles anyway. There is no garbage collector keeping the target alive while a pointer references it, and no compile-time lifetime tracking. (In Rust, by contrast, the borrow checker refuses to compile a pointer that could outlive its target; Odin makes a different trade — a much simpler language, and the lifetime discipline is on you.) When you allocate with new(Player), the storage lives until you call free — forget it and you leak; free twice and you corrupt the allocator.

not the same as a nil pointer A dangling pointer holds a once-valid address whose data is gone — the worst case, because reading it often succeeds and returns plausible garbage. A nil pointer is the zero value (p: ^int is nil until assigned), and a p == nil check is a cheap compare-to-zero you can test for. Forcing a real load through nil — y := bad^ then using y — is a hardware segfault, not a friendly Odin message. (A subtlety: fmt.println(bad^) alone prints <nil> without crashing, because fmt sees a nil data pointer and declines to load — you have to force the load to feel the crash.) Nil you can guard against; dangling you cannot detect after the fact.

The last level isn't about one pointer — it's the property that emerges from Odin splitting "pointer" into three distinct types: the type itself tells the reader what the author meant, and forbids the operations that wouldn't make sense.

In some languages one pointer type means "exactly one T", "the first of an unknown run of T", and "an arithmetic cursor" all at once, and you guess which from context. Odin gives each its own type. Click a column to see what each allows — and what the compiler rejects:

Two of those "no" cells are real compiler errors, not style advice. Indexing a single-value ^T, or doing arithmetic on it, simply has no operator — Odin has no pointer-arithmetic operators at all. p + 1 on a ^int:

x: int = 42
p := &x
q := p + 1   // step the pointer? there is no such operator

Error: Cannot convert untyped value '1' to '^int' from 'untyped integer'

And a multi-pointer refuses the opposite mistake — you can index it, but you cannot ^-dereference it, because "dereference which element?" has no answer:

mp: [^]int = raw_data(nums[:])
x := mp^     // deref which one?

Error: Cannot dereference 'mp' of type '[^]int'
    Did you mean 'mp[0]'?

The emergent payoff: because the three are different types, a function signature is a contract you can read. A parameter typed ^Player says "I will touch exactly one"; [^]c.int says "this came from a C library and I must carry the count separately"; []Player says "a bounded run I can iterate and the length rides along." The compiler enforces the difference — indexing a ^T won't compile, so the "is this one thing or many?" bug is caught at the type level instead of becoming a runtime read off the end of something. The cheapest move on this whole ladder is to climb to the lightest type that does the job: a multi-pointer from C bindings should be sliced into a []T the moment you know the length, and from there you never think about raw addresses again.

That's the arc: L1 a pointer is one 8-byte address, and the address aliases real storage → L2 that aliasing is the only way a proc can mutate the caller's data without copying → L3 the address knows nothing about lifetime, so keeping the target alive is your unguarded job → L4 Odin splits "pointer" into ^T / [^]T / []T so the type states the intent and the compiler forbids the nonsense.
